# Doris Profile Analyzer — руководство пользователя

Клиентское веб-приложение для анализа профилей запросов Apache Doris.
Помогает быстро найти узкое место в плане выполнения — медленный скан,
неэффективный фильтр, перекошенный join, проблему с памятью — не
отправляя профиль никуда за пределы вашего браузера.

---

## Зачем это нужно

Когда запрос в Doris работает медленно, FE может выдать
**Query Profile** — иерархическую структуру с тысячами счётчиков по
каждому оператору на каждом BE. В сыром виде это десятки тысяч строк
текста, в которых легко утонуть.

Этот инструмент превращает профиль в визуальные «срезы»:

- **где** в плане самый горячий оператор (Plan Tree, цветовая карта);
- **сколько** строк реально прочитано и сколько отфильтровано
  (Scan Summary, столбец Filter %);
- **есть ли перекос** между BE-инстансами одного оператора
  (Scan Summary / Join Summary, столбец Skew);
- **что дороже в join** — построение хеш-таблицы или прохождение
  (Join Summary, выделение Build Time оранжевым, если build > probe);
- **как фрагменты связаны между собой** через EXCHANGE / DATA_STREAM_SINK
  (Plan Tree, пунктирные межфрагментные рёбра).

Всё работает **локально**, в браузере. Никакого бэкенда, никаких
загрузок наружу. Подходит для анализа production-профилей без риска
утечки SQL или имён таблиц.

## Запуск

Сборки не требуется — это набор статических файлов.

```bash
# вариант 1: открыть index.html напрямую
# (на Windows достаточно двойного клика; некоторые браузеры
#  блокируют ES-модули по протоколу file:// — тогда вариант 2)

# вариант 2: локальный HTTP-сервер
python -m http.server 8000
# затем http://localhost:8000
```

Зависимостей нет. Никакого npm, node_modules, бандлеров. Любой
свежий Chrome / Firefox / Edge подойдёт.

## Какие форматы профиля поддерживаются

Doris отдаёт профиль тремя способами; приложение принимает все три:

1. **Текст из SQL-команды** — то, что вы видите после
   `SHOW QUERY PROFILE "/<query_id>"`. Просто скопируйте и сохраните в
   файл `.txt`.
2. **Текст из FE HTTP API** — `GET /api/profile_text?query_id=<id>`.
   Тот же формат, что и из SQL.
3. **JSON-обёртка FE HTTP API** — `GET /api/profile?query_id=<id>`.
   Возвращает `{"msg":"success","data":{"profile":"..."}}` —
   приложение автоматически распакует поле `data.profile` и
   распарсит как текст.

Определение формата — автоматическое: первая непробельная литера `{`
означает JSON, всё остальное — текст.

---

## Как загрузить профиль

Три способа:

- **Перетащить файл** в окно браузера. Поверх экрана появится оверлей
  «Drop profile here»; отпустите файл, и он загрузится.
- **Кнопка «Open profile…»** в верхней панели — стандартный диалог
  выбора файла.
- **`samples/tpch/*.json|.txt`** в репозитории — реальные TPC-H
  профили для тренировки и регрессионных тестов.

После загрузки в верхней панели появятся метаданные: имя файла,
размер, формат (`text` / `json`), Profile ID, Total время и Task
State. Если парсер встретил неоднозначности, рядом возникнет
жёлтая «бирка» `⚠ N warnings` — щёлкните по ней, чтобы развернуть
список с номерами строк.

## Вкладки

Каждая вкладка — отдельный «срез» одного и того же распарсенного
профиля. Между ними можно переключаться без перезагрузки.

### 1. Scan Summary

**Активна по умолчанию.** Таблица с одной строкой на каждый
`OLAP_SCAN_OPERATOR` в плане.

#### Столбцы

| Заголовок     | Что показывает                                              |
|---------------|-------------------------------------------------------------|
| ▸             | раскрыть / свернуть подробности по этому скану              |
| Table         | имя таблицы (без алиаса)                                    |
| Part/Tab      | партиции / тэблеты, привлечённые сканом                     |
| Cardinality   | оценка кардинальности от планировщика (cardinality=…)       |
| Rows Read     | сумма реально прочитанных строк по всем BE                  |
| Rows Prod     | сумма строк после фильтрации (то, что ушло наверх)          |
| Filter %      | доля строк, которые удалось отфильтровать на уровне скана   |
| ExecTime      | диапазон max…min по BE-инстансам                             |
| Skew          | max/min ExecTime — насколько неравномерна нагрузка между BE |
| Mem Peak      | пик памяти, занятой сканом                                  |

#### Цветовые подсказки

- **Filter %** ≥ 50 % — зелёный. Означает, что фильтры (Bloom,
  ZoneMap, runtime filter из join и т. д.) реально работают.
  Низкое значение — повод проверить, не доезжает ли runtime filter
  до этого скана, или не плохо ли расположены данные.
- **Skew** > 3× — жёлтый, > 10× — красный. Один BE работает
  кратно дольше остальных — типичная причина «хвоста» по времени.
- **ExecTime** — отображается как `min…max`, чтобы сразу видеть
  разброс.

#### Сортировка

Любой заголовок — кликабелен. Стрелка ▼ / ▲ показывает текущее
направление. По умолчанию сортируется по `ExecTime max` (от большего
к меньшему), чтобы сразу увидеть самые медленные сканы сверху.

#### Раскрытие строки (▸)

Внутри панели подробностей:

- **PlanInfo** — дамп всех ключей `PlanInfo.*` для этого скана:
  партиции, тэблеты, cardinality, pushAggOp, prefetched columns.
- **Per-instance** — таблица по каждой задаче (BE-инстансу) с
  колонками Host, ExecTime, Rows Read, Scanners, Mem Peak.
- **Filter breakdown** — сколько строк отфильтровал каждый тип
  фильтра отдельно: BloomFilter, ZoneMap, ShortCircuit,
  BitmapIndex, InvertedIndex.
- **Per-scanner skew** — min / median / max времени работы среди
  всех VScanner-потоков и их отношение. Полезно, когда перекос
  не между BE, а внутри одного BE (например, один тэблет
  оказался тяжёлым).

#### Типичные сценарии использования

- **«Запрос упирается в скан большой таблицы»** — открываете Scan
  Summary, сортируете по `ExecTime` и смотрите верхнюю строку. Если
  `Filter %` низкий, а `Rows Read` совпадает с `Cardinality` —
  runtime filter от join не прошёл, нужно искать почему.
- **«Один BE тормозит весь кластер»** — Skew подсветится цветом.
  Раскройте строку, посмотрите Per-instance — увидите, какой именно
  хост и насколько отстаёт.
- **«Память выросла на одной таблице»** — столбец Mem Peak покажет
  пик и поможет соотнести с настройками BE.

### 2. Join Summary

Таблица с одной строкой на каждый `HASH_JOIN_OPERATOR`. Probe-сторона
(сам HASH_JOIN_OPERATOR) и build-сторона (HASH_JOIN_SINK_OPERATOR)
автоматически сшиваются по общему `id` внутри фрагмента.

#### Столбцы

| Заголовок     | Что показывает                                                      |
|---------------|---------------------------------------------------------------------|
| ▸             | раскрыть подробности по join                                        |
| Join          | `F<fragment>/J<id>` — координаты в плане                            |
| Type          | `INNER JOIN`, `LEFT SEMI JOIN`, `RIGHT ANTI JOIN` и т. д.           |
| Distribution  | `BROADCAST` / `COLOCATE` / `PARTITIONED` / `SHUFFLE`                |
| Build Rows    | сколько строк ушло в построение хеш-таблицы (InputRows на sink)     |
| Probe Rows    | сколько строк прошло через probe-сторону                            |
| Build Time    | max BuildHashTableTime среди BE-инстансов                           |
| Probe Time    | диапазон ExecTime probe-стороны (min…max)                            |
| HashTbl Mem   | сумма MemoryUsageHashTable по всем BE                               |
| Skew          | max/min ExecTime по probe-стороне                                   |

#### Цветовые подсказки

- **Build Time** оранжевый — когда build занимает дольше, чем самый
  медленный probe. Сигнал, что узкое место — построение
  хеш-таблицы, а не прохождение по ней. Часто это маленькая по
  плану, но дорогая по реальности build-сторона.
- **Skew** — те же пороги, что и в Scan Summary (3× / 10×).

#### Раскрытие строки

- **PlanInfo** — `join op`, `equal join conjunct`, `runtime filters`,
  `cardinality`, `output tuple id` и так далее.
- **Build phase (per-instance times)** — сводка по сборке хеш-таблицы:
  - hash-table max / sum,
  - insert sum,
  - runtime-filter sum.
- **Build instances** — таблица с ExecTime, BuildHashTable,
  BuildRuntimeFilter, InputRows, HashTable Mem, Mem Peak по каждому BE.
- **Probe instances** — таблица с ExecTime, SearchHashTable, WaitDep,
  ProbeRows, RowsProduced, Mem Peak по каждому BE.

#### Типичные сценарии использования

- **«Не понимаю, почему этот join такой долгий»** — смотрите
  соотношение Build Time и Probe Time. Если build выделен
  оранжевым — оптимизатор недооценил build-сторону, можно попробовать
  COLOCATE/SHUFFLE вместо BROADCAST или поменять порядок join.
- **«Подозреваю spill»** — раскройте строку, проверьте Build instances
  на наличие колонок `Spilled*` (если профиль их содержит) и
  пики MemoryUsageHashTable.
- **«Distribution выглядит подозрительно»** — столбец Distribution
  сразу показывает, какой метод выбрал планировщик. BROADCAST на
  большой таблице — повод задуматься.

### 3. Plan Tree

Интерактивное **дерево всего плана** запроса, собранное из всех
фрагментов в одну схему. Узлы — операторы, рёбра — поток данных.

#### Что вы видите

- **Карточка узла** (160 × 56 px): короткое имя оператора
  (`OLAP_SCAN`, `HASH_JOIN`, `AGG`, `EXCH`, `RESULT_SINK` …),
  идентификатор `#id` справа, максимальный ExecTime крупно,
  тонкая «полоска нагрева» как второй визуальный канал.
- **Цвет карточки** — нагрев по ExecTime, нормированный **внутри
  фрагмента**. Самый горячий оператор фрагмента — красный, чуть
  холоднее — оранжевый, потом жёлтый, синий, серый. Так
  узкие места видно с одного взгляда даже на больших планах.
  Нормировка по фрагменту, а не по всему плану, потому что
  фрагменты могут отличаться по сумме времени на порядки.
- **Сплошные рёбра** — поток данных внутри фрагмента
  (parent ← child).
- **Пунктирные фиолетовые рёбра** — межфрагментные связи:
  `EXCHANGE_OPERATOR` сшит с соответствующим
  `DATA_STREAM_SINK_OPERATOR` по `dst_id`. Это позволяет
  увидеть, какой EXCHANGE на одном фрагменте получает данные
  от какого DATA_STREAM_SINK на другом.
- **Сканы — внизу, RESULT_SINK — наверху.** Дерево
  «снизу-вверх», как в EXPLAIN и в большинстве движков СУБД.

#### Управление видом

- **Колесо мыши** — масштаб (привязан к курсору, то есть точка
  под курсором остаётся под курсором).
- **Перетащить фон** — пан.
- **Кнопки + / −** в правом верхнем углу — масштаб от центра.
- **Кнопка Fit** — вписать всё дерево в окно (запускается
  автоматически при загрузке).
- **Клавиатура** (после клика по SVG-области):
  `F` — Fit, `+` / `−` — масштаб, `Esc` — закрыть боковую панель.

#### Боковая панель деталей

Щёлкните по любому узлу. Справа въедет панель с полным дампом
счётчиков этого оператора:

- **Заголовок** — имя оператора, его `id` и фрагмент.
- **PlanInfo** — все ключи `PlanInfo.*` оператора. Для join тут
  будет `join op`, условие, runtime filters и т. д.
- **Counters (merged)** — все остальные счётчики из merged-секции
  профиля (avg / max / min времена, объёмы памяти, количества строк).
- **Cross-fragment link** — для EXCHANGE-узлов: какой
  DATA_STREAM_SINK в каком фрагменте является «партнёром». Кнопка
  **Reveal in tree** центрирует и подсвечивает узел-партнёр.

Щёлчок по другому узлу мгновенно подменяет содержимое панели.
Esc или крестик ` × ` закрывают её.

#### Типичные сценарии использования

- **«Где затык?»** — глаза на красные узлы в каждом фрагменте.
  Это всегда подсказка, на чём сфокусироваться.
- **«Куда идут данные после EXCHANGE?»** — щёлкните EXCHANGE,
  нажмите Reveal in tree → видна следующая ступень плана и её
  фрагмент.
- **«У оператора большой WaitForDependency»** — Counters в панели
  покажет это поле. Высокий WaitForDependency на этом операторе
  означает, что **upstream** медленнее; смотреть нужно не сюда,
  а на источник.

### 4. Raw

Сырая текстовая версия профиля с номерами строк и сворачиванием по
уровню отступа. Удобно для:

- грепа значений, которые не выведены в типизированных вкладках;
- проверки гипотезы из других вкладок («а действительно ли тут
  такой счётчик?»);
- быстрого просмотра PlanInfo секций для операторов, которые ещё
  не получили типизированный вид (SORT, ANALYTIC, NESTED_LOOP_JOIN
  и т. д.).

Щёлкните по треугольнику ▾ слева — соответствующий блок
свернётся. Полезно, чтобы скрыть огромную секцию
`Changed Session Variables` или массивный Pipeline.

## Заголовочная панель

Над вкладками всегда видна сводка:

- **file** — имя загруженного файла;
- **size** — размер в KB / MB;
- **format** — `text` или `json`;
- **Profile ID** — `query_id`, по которому профиль был получен;
- **Total** — общее время выполнения;
- **Task State** — финальный статус (FINISHED / ERROR / CANCELLED);
- **⚠ N warnings** (если есть) — кликабельная бирка с журналом
  предупреждений парсера (например, «counter at unexpected indent»).
  Полезно при отладке необычных профилей или новых версий Doris.

## Общий рабочий процесс для оптимизации запроса

Один из типичных сценариев — у вас есть медленный запрос. Что делать?

1. **Получите профиль.** В Doris:
   ```sql
   SET enable_profile = true;
   -- ваш SQL
   SHOW QUERY PROFILE "/<query_id>";
   ```
   или через FE HTTP `GET /api/profile?query_id=<id>`.

2. **Откройте профиль** в Doris Profile Analyzer (drag-and-drop
   файла или Open profile…).

3. **Plan Tree → найдите красные узлы.** Глаза по верхушке —
   самый «горячий» оператор каждого фрагмента подсвечен. Это
   ваши кандидаты на оптимизацию.

4. **Если узкое место — скан**, переключитесь на Scan Summary:
   - Посмотрите Filter % этой таблицы. Низкое значение → runtime
     filter не пришёл / не сработал.
   - Посмотрите Skew. Если > 10× — проблема с распределением
     данных по BE (нужно проверить ключ распределения / тэблеты).
   - Раскройте строку → Filter breakdown подскажет, какой фильтр
     помог, а какой нет.

5. **Если узкое место — join**, переключитесь на Join Summary:
   - Distribution → BROADCAST на большой таблице? Возможно,
     планировщик не справился, попробуйте `[shuffle]` / `[colocate]`
     хинты.
   - Build Time оранжевый → build-сторона дороже probe, проверьте
     порядок join.
   - HashTbl Mem огромный → возможно, нужно понизить кардинальность
     build-стороны фильтром.

6. **Если непонятно**, откройте Raw → найдите оператора по `id`
   (видимо в Plan Tree на карточке как `#N`) → посмотрите все
   счётчики целиком.

7. **При сравнении версий** — пока что Compare-режима нет (это
   запланированная итерация 6), используйте две вкладки браузера.

## Что приложение **не** делает

Намеренные ограничения — чтобы оно оставалось простым, локальным и
понятным:

- **Не подключается к Doris.** Никаких CORS-ходоков из браузера в FE.
  Профиль вы выгружаете сами.
- **Не предлагает rewrite SQL.** Это инструмент диагностики, а не
  оптимизатор.
- **Не хранит профили.** Никаких аккаунтов, истории, шеринга.
  Закрыли вкладку — данных нигде нет.
- **Не сравнивает два профиля.** Запланировано, но пока вручную.
- **Не визуализирует per-host metrics для операторов кроме
  OLAP_SCAN и HASH_JOIN.** Они есть в Raw и в боковой панели Plan
  Tree, но без типизированных таблиц.
- **Не показывает временную диаграмму фрагментов (Gantt).**
  Тоже в планах.

## Конфиденциальность

Это **client-side** приложение. Весь код — JavaScript, исполняемый
в браузере. Файл профиля читается через `File.text()`, парсится в
памяти и отображается. **Никаких сетевых запросов с содержимым
профиля не делается.**

Можно работать даже офлайн: откройте `index.html` локально или
запустите `python -m http.server 8000` без интернета.

Если ваш профиль содержит чувствительный SQL или имена таблиц,
анализ всё равно безопасен — он не покидает машину.

## Хитрости и советы

- **Большие профили** (> 10 MB): парсинг и рендеринг занимают
  несколько секунд. Plan Tree → Fit может выглядеть мелко при
  500+ узлах; используйте +/Колесо для приближения к интересному
  фрагменту.
- **JSON ≡ Text**: оба формата дают идентичные данные (это
  гарантируется тестами). Используйте то, что удобнее скачать
  из вашего FE.
- **Skew > 3× — не всегда баг.** Иногда это естественная
  гранулярность тэблетов. Смотрите Per-scanner skew внутри
  раскрытой строки скана: если перекос внутри одного BE — это
  data skew, между BE — distribution skew.
- **WaitForDependency на операторе ≠ медленный оператор.** Высокое
  значение этого счётчика означает, что **этот** оператор ждал
  upstream. Узкое место — выше по плану (или, в bottom-up
  визуализации, ниже).
- **Filter % близко к 100 % при больших Rows Read** — фильтр работает
  отлично, но кардинальность ещё высокая. Возможно, имеет смысл
  раньше отсечь данные (по партиции, индексу, runtime filter).

## Минимальная справка по форматам Doris

### Иерархия профиля

```
Query Profile
├── Summary                 # query_id, sql, time, state
├── Execution Summary       # агрегаты
└── Fragment N              # один на FE-фрагмент
    └── Pipeline N          # один pipeline в фрагменте
        └── PipelineTask N  # параллельная задача на BE
            └── Operator
                ├── ExecTime               # активное время
                ├── WaitForDependencyTime  # ожидание upstream
                ├── PeakMemoryUsage
                └── (специфика оператора)
```

### Ключевые операторы

| Имя в профиле                  | Что это                                   |
|--------------------------------|-------------------------------------------|
| `OLAP_SCAN_OPERATOR`           | чтение из таблицы OLAP-движка              |
| `HASH_JOIN_OPERATOR`           | probe-сторона hash join                   |
| `HASH_JOIN_SINK_OPERATOR`      | build-сторона hash join                   |
| `AGGREGATION_OPERATOR`         | GROUP BY                                  |
| `EXCHANGE_OPERATOR`            | приёмник межфрагментной передачи          |
| `DATA_STREAM_SINK_OPERATOR`    | отправитель межфрагментной передачи       |
| `LOCAL_EXCHANGE_OPERATOR`      | внутрифрагментная передача между pipeline |
| `SORT_OPERATOR`                | ORDER BY / TopN                           |
| `RESULT_SINK_OPERATOR`         | возврат данных клиенту                    |

`dst_id` на `EXCHANGE_OPERATOR` и `DATA_STREAM_SINK_OPERATOR`
совпадают для парных узлов — именно по нему Plan Tree сшивает
межфрагментные рёбра.
