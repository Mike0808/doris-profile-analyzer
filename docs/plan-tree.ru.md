# Plan Tree — как устроено дерево плана

Простое объяснение того, как вкладка **Plan Tree** превращает разрозненный
текст профиля в одну связную схему запроса. Это документ «как оно работает
внутри»; если нужно «как пользоваться» — смотрите раздел
[Plan Tree в руководстве пользователя](./user-guide.ru.md#3-plan-tree).

Код: [`js/render/planTree.js`](../js/render/planTree.js) (раскладка + отрисовка),
[`js/parser/planTree.js`](../js/parser/planTree.js) (сборка модели дерева).

---

## Что показывает дерево

Это **карта пути данных** внутри запроса. Каждый прямоугольник — операция
(прочитать таблицу, соединить, отсортировать, сгруппировать). Данные текут
**снизу вверх**: внизу — сканы таблиц (`OLAP_SCAN`), наверху — `RESULT_SINK`,
откуда результат уходит клиенту. Линии — это «кто кого читает».

---

## Почему данные приходят кусками (главная сложность)

Doris не хранит готовый цельный план. Он режет запрос на части, и в профиле
лежит набор отдельных кусочков:

- **Фрагменты** — части, выполняемые на разных машинах. Между ними обмен по
  сети: `EXCHANGE_OPERATOR` (приёмник) ↔ `DATA_STREAM_SINK_OPERATOR`
  (отправитель), связаны общим `dst_id`.
- **Пайплайны** — внутри одного фрагмента план дополнительно режется в местах,
  где приходится «остановиться и накопить» (сортировка, построение
  хеш-таблицы, агрегация). Один кусок заканчивается приёмником
  `*_SINK_OPERATOR (id=X)`, а другой кусок начинается источником
  `*_OPERATOR (id=X)` с **тем же номером id**.

Например, во фрагменте TPC-H Q3 девять пайплайнов, сшитых попарно:
`AGGREGATION_SINK(6)`→`AGGREGATION(6)`, `HASH_JOIN_SINK(5)`→`HASH_JOIN(5)`,
`LOCAL_EXCHANGE_SINK(-8)`→`LOCAL_EXCHANGE(-8)` и так далее.

Если эти стыки не склеить, каждый кусок повиснет отдельной карточкой — именно
так выглядел баг, когда дерево превращалось в «забор» из несвязанных карточек
в один ряд.

---

## Как код собирает из кусочков одно дерево

Узлы соединяются двумя видами связей:

1. **`childrenIdx`** — обычные «дети» внутри одного куска (операторы, вложенные
   друг в друга по отступам в тексте профиля).
2. **Ссылка на «напарника»** — склейка кусочков. У узла-потребителя хранится
   указатель на тот кусок, который его кормит:
   - `EXCHANGE` → его `DATA_STREAM_SINK` через сеть — поле `crossFragmentLink`;
   - источник `*_OPERATOR(id=X)` → его `*_SINK(id=X)` в том же фрагменте — поле
     `pipelineLink`.

Сшивка `pipelineLink` устроена так: для каждого `*_SINK_OPERATOR`, который
оказался корнем пайплайна, ищется единственный источник с тем же
`(fragmentId, opId)`, не являющийся сам по себе sink-ом. `DATA_STREAM_SINK`
(межфрагментный) и `RESULT_SINK` (корень всего запроса) в этой сшивке не
участвуют. См. [`buildPlanTree`](../js/parser/planTree.js).

Ключевая идея для раскладки — функция
[`childrenForLayout`](../js/render/planTree.js): «дети узла = его обычные дети
**плюс** его напарник (если есть)». После этого весь запрос — это **одно
дерево** от корня `RESULT_SINK`, и неважно, что физически он был нарезан на
много кусков. Напарник добавляется последним, поэтому у join-а build-сторона
(связанный sink) аккуратно встаёт справа от probe-стороны (обычный ребёнок).

---

## Как считаются координаты

Три шага, все «растут» из корня по `childrenForLayout`:

1. **`computeDepths`** — обход в ширину от корня. Глубина узла = вертикальный
   уровень (Y). Напарник всегда на один уровень ниже того, кто его читает.
   Если какой-то пайплайн остался несвязанным (например, sink без пары), он
   «якорится» на минимальной глубине своего фрагмента, чтобы тоже получить
   позицию.
2. **`computeSubtreeWidths`** — снизу вверх считает, сколько места по
   горизонтали нужно каждому поддереву: лист = ширина одной карточки
   (`NODE_W`), узел с детьми = сумма ширин детей плюс зазоры (`H_GAP`). Это
   резервирует место, чтобы соседи не наезжали друг на друга.
3. **`layoutPlan`** — сверху вниз раздаёт X-координаты: ставит узел по центру
   отведённой ему ширины, а детей раскладывает слева направо. Поскольку
   напарник теперь учтён в ширине родителя, межфрагментное/межпайплайновое
   поддерево встаёт **прямо под** тем, кто его читает, не задевая соседей.
   Любое по-настоящему несвязанное поддерево размещается справа от всего
   остального.

## Линии и цвета

Три типа рёбер (стили в [`css/styles.css`](../css/styles.css), `path.edge*`):

| Линия                              | Что означает                                   |
|------------------------------------|-------------------------------------------------|
| сплошная серая                     | родитель ← ребёнок внутри пайплайна             |
| мелкий бирюзовый пунктир (`.pipeline`) | стык пайплайнов внутри фрагмента (sink → source) |
| крупный фиолетовый пунктир (`.xfrag`)  | обмен между фрагментами по сети                 |

**Цвет карточки** — «температура» по `ExecTime`, нормированная **внутри
фрагмента**: чем краснее, тем больше время оператора относительно самого
медленного в его фрагменте (см. `heatClass`). Так узкие места видно с одного
взгляда. Нормировка по фрагменту, а не по всему плану, потому что фрагменты
могут отличаться по суммарному времени на порядки.

## Интерактив

- **`attachPanZoom`** — зум колесом (привязан к курсору), пан перетаскиванием
  фона, кнопки `+ / − / Fit`, горячие клавиши `F` (вписать), `+/−`.
- **`attachDetailPanel`** — клик по узлу открывает боковую панель со всеми
  счётчиками оператора. Для узлов со связью показывается секция
  **Cross-fragment link** или **Pipeline link** с кнопкой **Reveal in tree**,
  которая центрирует и подсвечивает узел-напарник.

## Мини-пример: TPC-H Q3

Так выглядит восстановленное дерево (`⇢` — связь-напарник):

```
RESULT_SINK#0 → EXCH#8 ⇢ STREAM_SINK#8 ⇢ LOCAL_EXCH#-10 ⇢ … → HASH_JOIN#5
                                                              ├─ OLAP_SCAN#4   (lineitem, probe)
                                                              └─ HASH_JOIN_SINK#5 ⇢ … → HASH_JOIN#3
                                                                                       ├─ … → OLAP_SCAN#2 (orders)
                                                                                       └─ … EXCH#1 ⇢ OLAP_SCAN#0 (customer)
```

Читается как обычный план: `customer ⋈ orders ⋈ lineitem` → агрегация →
сортировка → сбор результата. Build-сторона каждого join (`*_SINK`) и
probe-сторона (`OLAP_SCAN`) ветвятся правильно.
